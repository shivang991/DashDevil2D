## Retained Stage 4 diagnostic

Issue [#29](https://github.com/shivang991/DashDevil2D/issues/29). This is a real network diagnostic, using the shared protocol v1 codecs and a frozen continuation derived from the independently reviewed #27 fixture. It does not start multiplayer rounds or supply a gameplay fallback. Gameplay authority/parity belongs to #28; complete lobby/countdown/play/results belong to later stages.

`POST /admission` accepts one binary AdmissionRequest frame and returns one Admission or ProtocolError frame. Operations are create/join/resume. The four-digit room code is returned in `X-Room-Code` (exposed to the allowed client origin); internal room identity is independent of the code. Credentials are random opaque 256-bit values. Each channel gets its own 30-second single-use ticket, bound to origin, seat/session, connection generation and channel. Resume rotates the generation and closes the old pair; retries cannot extend the original disconnected reservation. A newly allocated seat has 15 seconds to complete initialization. Explicit leave invalidates the credential; idle rooms expire after 15 minutes. Capacity defaults to 50 rooms including reservations in every phase. `--room-limit` configures the process admission limit from 1 to 10000; available seats and valid reconnects in existing rooms remain eligible at capacity.

`/room?ticket=…` upgrades only allowed-origin secure WebSockets. The client echoes RoomInitialization to acknowledge the bound room identity. `/gameplay?ticket=…` is a real HTTP/3 extended CONNECT on UDP in the same process. Its three application streams are client-opened bidirectional control, client-opened unidirectional inputs and server-opened unidirectional authority. HTTP/3's own streams have a separate connection limit. Additional application streams and client datagrams fail the pair. Room and gameplay initialization can arrive in either order; connected/readiness eligibility requires both room initialization and an installed baseline acknowledged by Ready. The diagnostic only accepts released-control input refreshes and readiness/leave room commands; it rejects round start and gameplay inputs explicitly.

The fixture retains float64 positions `100.125` and `20000.5`, HP, scores, generation state, coverage and consumption from `packages/contracts/protocol/fixtures.json` v1. It clears held/effective controls and movement timers, and assigns current seat/pair/input identities. Heartbeat ticks identify frozen diagnostic continuations; they are not simulation ticks proving movement parity. Baselines use bounded authority chunks. A recovery request sends another complete baseline with a fresh epoch and transfer identity; barriers/datagrams resume after its matching Ready. The browser compares CRC32C at the matching barrier, retains at most 20 ticks, discards unknown epochs/malformed datagrams and coalesces drift recovery requests.

Reliable frames are bounded before allocation (64 KiB), baselines at 1 MiB, a shared per-pair queue budget of 256 KiB/512 messages including writes in flight, writes/queue waits at 500 ms, and outstanding application progress at one second. The current fixture fits one 1,057-byte baseline; larger transfers are chunked. Chunk production waits for drained queue space and fails the pair on a 500 ms stall; it does not enqueue a full large transfer ahead of the writers. Input/room rate is 60/s with burst 120; clock requests 2/s, recovery 1/s and one outstanding. Old identities, stale sequences and expired credentials cannot become fresh input. Both channels close together on loss or protocol/resource failure. The server logs internal identifiers, baseline bytes/install duration and application acknowledgement/queue progress, never credentials or ticket URLs. These application measurements are not network-byte totals including QUIC/IP overhead.

## Run locally

Use the pinned Node/pnpm/Go versions. Install `mkcert` and establish its local development CA with `mkcert -install`. Then, from the root:

```sh
pnpm dev:transport --diagnostic
```

Open [the diagnostic page](https://127.0.0.1:4173/transport.html) in two separate tabs. Vite serves trusted HTTPS on 4173; Fiber HTTPS/WebSockets and HTTP/3 UDP share 8443. The explicit allowed website origin includes port 4173. `mkcert` supplies the HTTPS certificate; WebTransport uses a separate ECDSA P-256 certificate, valid for 13 days plus a one-hour NotBefore margin (under 14 days), authenticated by its SHA-256 fingerprint. Keys are kept in ignored `.local/transport` with private permissions. Each startup renews the WebTransport certificate if less than two days remain, and atomically updates its public fingerprint configuration. `pnpm dev:transport --diagnostic --renew` forces rotation and restarts the listeners. Restart long-running development sessions before expiry. No machine trust store is modified by our commands; `mkcert -install` is an explicit local prerequisite.

For production, build the client and invoke `go run ./cmd/diagnostic --diagnostic --address :443 --origin https://your-host --cert trusted.pem --key private.pem --static ../client/dist` from this module. Supply real TCP **and UDP** ingress. Omit development QUIC certificate flags: both listeners use normal trusted certificates. The production client uses normal certificate validation and receives no development hash configuration. A listener failure terminates the process; a restart starts empty. This diagnostic is not a complete multiplayer production service.

## Verification and limitations

`pnpm test:transport` builds/starts the native server and HTTPS Vite, generates an isolated short-lived certificate, and launches actual installed Chrome with a public-key-scoped local HTTPS trust pin. WebTransport independently verifies its SHA-256 certificate hash. It uses no global certificate bypass or UDP/gameplay fallback. This automated test does **not** establish OS-level mkcert trust or the full browser-release matrix. It retains each run's sanitized manifests, logs, per-seat state, screenshots and video in `apps/client/test-results/transport-*`; private keys/seat credentials/tickets are excluded, and network traces are disabled to avoid recording bearer credentials. Original failures remain alongside retries.

Native `go test ./...` covers HTTPS admission/version/origin errors, opaque credentials, ticket channel/origin/single-use binding, real QUIC streams/datagrams/CRC/clocks, baseline epoch recovery, pair loss/replacement, missing application progress, oversized room frames and reconnect expiry across ticket retries. `go test -race ./transport` checks concurrent teardown/ownership. `pnpm test:transport` is mandatory in CI alongside existing generated-output, Vitest, Go, build and Long Drive browser preservation checks.

Current/previous Chrome, Edge, Firefox and Safari on applicable Windows/macOS, OS-trusted local certificate interoperability, impairment profiles, network overhead measurements, reference hardware and manual evidence remain explicit acceptance work. Automation engines alone cannot establish those checks. Combine actual transport evidence with #28 independently reviewed gameplay parity for the Stage 4 exit; do not proceed to Stage 5 while that gate is incomplete. See [checkpoint](../../../docs/preservation/transport-checkpoint.md).
