## Capacity-discovered watchdog defect

An aged paired connection retained `restoredAt` from its initial admission. Every new valid round `Initialization` clears the previous baseline, but the watchdog compared that temporary absence against the original connection timestamp. Once the pair was five seconds old, a normal gap between control Initialization and authority baseline delivery could cause immediate “Initialization timed out”, paired recovery and countdown cancellation. `full-5` retained this exact symptom.

The client now owns a separate `initializationStartedAt`: initialize it on connection setup and reset it for each valid Initialization. Keep the existing five-second client timeout, original recovery timing origin and server baseline/progress deadlines unchanged. No gameplay correction or numeric target relaxation is introduced.

Both-mode native-transport regressions age a real pair six seconds, observe the new control Initialization, then delay the actual framed baseline chunk 350 ms. They require a new usable baseline in both seats, the same connection identities and no errors. Before the fix, both modes failed with exactly “Initialization timed out”; existing lifecycle scenarios passed. After the fix, all four lifecycle scenarios passed. Original red and green runs: `transport-2026-10-26T00-19-36.984Z` and `transport-2026-10-26T00-21-10.527Z`. The fixture is an application-reader delay, not an actual network impairment profile.

Fix revision: `8f4bded`. Independent Spec review found no actionable defect and supported the causal red/green regression. Standards found no documented violation, with one nonblocking numeric-domain-constant heuristic in the load harness. Forced workspace checks again passed 15/15, including 434 Vitest tests and Go checks. Real-transport smoke passed 3/3; both dense baseline/progress-deadline scenarios passed 2/2. Preservation passed all 12 scenarios after this fix. Client fix deployment passed HTTPS/HTTP3 readiness. The next load attempts and additional correction follow.

The first worker topology put 98 players in one browser context. Chromium applies [per-renderer concurrent WebSocket handshake throttling](https://chromium.googlesource.com/chromium/src/+/b0627068678d2062ecf4948e391e3901d0cd3db8/services/network/websocket_throttler.cc); shared-context scheduling/throttling is therefore a testable generator hypothesis, not proof that every server failure was a generator artifact. Later attempts group five rooms per isolated browser context and retain native WebSocket/WebTransport open/error intervals without URLs or tickets. No browser throttle, transport, certificate check or product deadline is disabled.

The harness now requires a recovered seat's room-channel identity generation to match its admission generation and its authoritative room seat to be initialized. A frozen old room view or gameplay-only status cannot establish paired restoration. Finalized recovery requires a matching authoritative outcome; active recovery requires released controls. Explicit stale room-command rejections can be retried at most three times within the existing lifecycle deadline, retaining each rejected revision. Other errors and timeouts still fail.

Clock RTT snapshots read each transport agent's bounded eight-sample clock-exchange history without changing the transport. These application-clock observations include delivery/scheduling effects and are not physical display timings. The product's existing `recoveryMs` field is overwritten by later room updates, so its growing values are not reliable completed-recovery latency measurements. Do not derive recovery-target percentiles from that field. Harness drop-to-paired-restoration duration and actual native handshake times are separate observations; neither is physical display timing.

This is qualitative owner review; no measured input-to-display percentiles, reference-client browser matrix or reproducible network impairment profile was supplied. ## Final load result and approved blocker

`full-9-contexts` reached 100 players and verified both-mode recovery, but failed coordinated lifecycle at cycle 6 before 30 minutes. Kernel UDP receive-buffer drops were observed. The harness had already failed and closed at `2026-10-26T01:10:31.855Z`, before the subsequent host intervention at `01:12:08Z`; the restart did not cause this run's failure. Retain the intervention timestamp and original pre-intervention server log.

Following the upstream [quic-go UDP-buffer recommendation](https://github.com/quic-go/quic-go/wiki/UDP-Buffer-Sizes), host `net.core.rmem_max` and `net.core.wmem_max` changed from 212992 to 7500000. Restarted server sockets report `rb14680064/tb14680064` (Linux accounts doubled socket buffers). The warning disappeared and public HTTPS/HTTP3 probes passed. The dedicated `/etc/sysctl.d/60-dashdevil-quic.conf` preserves these ceilings across reboot; its contents match the tracked [host configuration](../../infra/quic.conf). No existing conflicting file was overwritten. Rollback: remove this dedicated file, restore both prior ceilings with `sysctl -w`, then use the normal drain/deployment flow to reopen sockets. This is an operational correction, not a relaxed product threshold.

`full-10-udp-buffers` used the tested server/client source and five rooms per browser context. Full capacity began `2026-10-26T01:16:30.250Z`; the connected-player gate failed at `01:20:47.393Z`, after **257143 ms (4 minutes 17 seconds)**, with 59/100 Connected at the gate sample and 47/100 in the later failure capture. It verified **98 deliberate same-seat recoveries: 48 Drag Race, 50 Road Rage**. Unexpected resets, authority application-progress timeouts and expired-authority recovery still occurred. Collection failed; there is no 30-minute pass.

Within that full-capacity interval, 127 resource samples recorded peak process CPU **80.60% of one core**, mean **43.82%**, and peak RSS **82.86 MiB**. UDP counters recorded **zero receive/send-buffer errors**. Entry probes observed maximum simulation-sweep gap **181.71 ms** and 456 GC stop-request/restart-entry intervals, maximum **1.223 ms**. Neither proxy supplies complete per-room tick or runtime-pause distributions. The collector continued after failed-driver cleanup until its 40-minute limit; summaries explicitly filter the load interval rather than treating later idle samples as capacity evidence. Post-cleanup resource/socket data remains retained; retained Go heap/RSS alone does not establish a leak or absence of one.

A subsequent six-player public-path diagnostic (`path-pilot-3`) completed 101754 ms, six canonical rounds per room and recovery in both modes. It also retained unexpected transport resets; collection completion is not a correctness/performance pass. Per-player final bounded application-clock RTT windows ranged from **257.8 to 501.5 ms**. Independent five-packet ICMP measurement recorded **255.311/268.803/290.323 ms minimum/mean/maximum**, zero observed loss in this small sample. This is not a qualifying impairment scenario or statistical loss bound, but it confirms that the current path cannot establish the normal-condition ≤150 ms RTT envelope. Backend TCP `ss` RTT observations describe nginx/server bridge connections and must not be reported as public-path RTT.

The owner explicitly selected **“Record blocker; keep open”** after receiving the public-path finding. Keep #44 open. A suitably located load-generator/reference-client environment, the sustained 50-room run and the remaining normal-quality measurements are still required. No timing/authority deadline, configured capacity or acceptance target was relaxed to force a pass.
